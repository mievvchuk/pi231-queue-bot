# Telegram-бот електронної черги ПІ-231

Бот керує тимчасовими чергами студентів на здачу лабораторних і практичних робіт.
Стек: Python 3.11+, aiogram 3, PostgreSQL (робочий запуск), SQLite (локальні тести), FSM.

Gitflow, порядок релізу, бан і перемикання режимів: [CONTRIBUTING.md](CONTRIBUTING.md).
Усі параметри середовища й підготовка до перезапуску: [docs/CONFIGURATION.md](docs/CONFIGURATION.md).

## Запуск (Windows PowerShell)

```powershell
python -m venv .venv
.\.venv\Scripts\pip install -r requirements.txt
Copy-Item .env.example .env      # впишіть BOT_TOKEN, DATABASE_URL та OWNER_ID
.\.venv\Scripts\python -m queue_bot.check_config
.\.venv\Scripts\python bot.py
```

Файл `.env` у git не потрапляє (`.gitignore`). Змінні середовища мають пріоритет над `.env`.

Змінні середовища:

| Змінна | Призначення |
|---|---|
| `BOT_TOKEN` | токен бота (у коді не зберігається) |
| `OWNER_ID` | обов'язковий Telegram ID власника без персонального значення в коді |
| `INITIAL_ADMIN_IDS` | ID початкових адмінів через кому; застосовується лише коли в базі немає адмінів |
| `DATABASE_URL` | обов'язкове підключення до БД; вбудованого пароля чи автоматичної нової бази немає |
| `TEST_DATABASE_URL` | тільки окрема тестова PostgreSQL для інтеграційних тестів; не робоча база |
| `SUBJECTS_PATH` | файл предметів; типовий шлях `data/subjects.json`, з підтримкою старого файла в корені |
| `SCHEDULE_PATH` | файл розкладу; типовий шлях `data/schedule.json`, з підтримкою старого файла в корені |

Свій Telegram ID можна дізнатися, наприклад, у бота @userinfobot.

## Тести

```powershell
.\.venv\Scripts\python -m pytest
```

Токен не потрібен: тестується бізнес-логіка на тимчасовій SQLite-базі.
PostgreSQL-тести виконуються за наявності `TEST_DATABASE_URL`; CI піднімає окремий PostgreSQL 16.

Перенесення того самого `DATABASE_URL` з коду в середовище не стирає дані. Перед релізом
задайте його в налаштуваннях хостингу. Нова міграція лише додає nullable-поле `banned_until`;
існуючі користувачі, черги та історія зберігаються. Перед міграціями зробіть резервну копію.

## Структура

```
bot.py                    сумісна команда запуску для хостингу
queue_bot/
  application.py          запуск і завершення процесу та фонових задач
  config.py               усі параметри середовища та їх перевірка
  check_config.py         безпечна перевірка налаштувань без мережі
  routing.py              порядок роутерів та middleware
  web.py                  HTTP healthcheck
  storage/database.py     SQLite/PostgreSQL, міграції, транзакції
  services/               бізнес-логіка, розпізнавання та каталог предметів
  handlers/               Telegram-інтерфейс студента, розкладу, банів
    admin/                окремі модулі черг, користувачів, предметів,
                          розкладу, звітів і налаштувань; спільні стани
data/                     початкові subjects.json та schedule.json
tests/                    регресійні й PostgreSQL-перевірки
docs/                     конфігурація та плани
```

## Як це працює

- **Примітки над таблицею замін.** ШІ читає загальні вказівки в шапці разом із рядками групи. Наприклад, «4-ті пари за розкладом четверга / перша пара / знаменник» підставляє на четверту пару предмет, викладача й аудиторію першої пари четверга знаменника зі збереженого `schedule.json`, навіть коли рядка ПІ-231 у таблиці немає. Конкретна заміна для групи має пріоритет; «По розкладу» зберігає загальну вказівку, а явно зазначені викладач/аудиторія уточнюють її. Результат і примітка з'являються в наявному попередньому перегляді перед підтвердженням адміністратора. Нерозбірливі примітки та відсутні вихідні пари потребують уточнення. Використовується наявний провайдер і ключ розпізнавання.
- **Обмін місцями.** Один запит без відповіді між двома студентами в конкретній черзі, включно зі зворотним запитом. На відповідь є 10 хвилин від надсилання; після цього можна надіслати новий. Прострочені запити без відповіді не змінюють позицій. Строк зберігається після перезапуску. Старе повідомлення може залишатися в Telegram, але його прострочений запит уже недійсний. Після відмови чи помилки доставки повторне надсилання доступне одразу. Погоджений обмін залишається повторюваним за попереднім рішенням власника, доки записи студентів не змінено/видалено.
- **Лабораторні та час.** Після вибору місця студент позначає конкретні лабораторні кнопками або вводить номери через кому, наприклад `1, 2`. Бот показує сумарний максимум і запитує особистий час від 5 хв до цієї межі. Для КПЗ №1 + №2 це 25 + 10 = 35 хв. Місце займається після підтвердження всіх даних. У «Моє місце» / «Дії» → «🧪 Обрати лабораторні» можна змінити перелік без втрати позиції; «⏱ Час здачі» змінює лише час. Старим записам номери не вигадуються.
- **Підтвердження здачі.** «✅ Здав» пропонує вибрати, які саме роботи з поточного запису здані. При частковій здачі студент залишається на тому самому місці з рештою лабораторних; їхній ліміт перераховується, особистий час обмежується новим максимумом. Після здачі всіх вибраних робіт студент виходить із черги. Застарілі кнопки не можуть змінити новий запис або чернетку.
- **Курсова та консультації.** Для курсової з КПЗ, черг типу consultation і предметів без лабораторного каталогу немає запитань про лабораторні, кількість або час. Запис і завершення працюють одразу. Проєкт інтерфейсів користувача ПС виключено з цієї фічі; каталог лабораторних не відновлює видалених черг.
- **Ролі.** `student` і `admin`. Кожна адмін-операція в `services/` викликає `require_admin`,
  тому перевірка відбувається на сервері, а не лише в меню. Початкові адміни з
  `INITIAL_ADMIN_IDS` додаються, тільки якщо таблиця `admins` порожня. Останнього адміна видалити не можна.
- **Черги.** Статуси `open` → `closed` → `archived`. Для комбінації «предмет + викладач + тип» може бути лише
  одна незавершена черга (частковий унікальний індекс).
- **Позиції.** Єдина функція `_set_order` розставляє 1..N без пропусків. Унікальні індекси забороняють
  дубль студента й дубль позиції; запис іде через `BEGIN IMMEDIATE`, тому одночасні запити безпечні.
- **Здача та вихід.** Запис не видаляється, а отримує статус `completed`, `left`, `removed` або
  `transferred`; історія зберігається, активні позиції перераховуються.
- **Завершення заняття.** Архівування, створення нової черги й перенесення виконуються в одній
  транзакції. Перенесені студенти ставляться на позиції, які вибрав адмін. Проміжні позиції стають
  зарезервованими «вільними місцями», які студент може обрати явно (запис у кінець їх не займає; тому в прикладі
  «1. Новий, 2. Шевченко, 3. Новий, 4. Мельник» нумерація лишається послідовною).
- **Журнал.** Адмін-дії пишуться в таблицю `admin_log`.
- **Міграції.** Схема версіонується через `PRAGMA user_version`; існуюча база не видаляється.
  Нові зміни додаються в кінець списку `MIGRATIONS` у `queue_bot/storage/database.py`.
- **Застарілі кнопки.** Невідомі або прострочені inline-кнопки отримують підказку натиснути `/start`.

## Обмеження

Ліміти зберігаються окремо в `data/lab_catalog.json`:

| Предмет | Перелік | Максимум кожної |
|---|---|---|
| Програмування в Інтернет | №1–7 | 40 хв |
| Людино-машинна взаємодія | №1–10 | 15 хв (орієнтир 10–15) |
| Машинне навчання | №1–7 | 30 хв |
| Архітектура та проєкт ПЗ | №1–3 | 20 хв |
| Конструювання ПЗ | №1–11 | 25, 10, 10, 15, 10, 15, 20, 15, 15, 15, 15 хв |

Назви для машинного навчання №1–3 взято з наданих методичок; інші роботи поки позначені номерами. Варіанти/частини ЛМВ №6 не створюють додаткових номерів понад погоджені 10.

- FSM використовує `MemoryStorage`: після перезапуску бота незавершені діалоги (ввід ПІБ, перенесення)
  потрібно почати знову. Усі дані черг і користувачів зберігаються в SQLite.
